### The "weakened statement" concern is refuted

Recent work added a third upward-closure conjunct (`S.modelBot`) to `openBranch_countermodel`
and a matching premise to `tableau_complete`'s `hvalid`. This is the kind of change that can
quietly hollow out a completeness theorem, so it was checked directly.

The generic lemma (`Tableau/Intuitionistic/Scheme.lean:9865-9871`) does carry the extra
conjunct. But the **public** theorems do not:

```lean
theorem intuitionisticTableau_complete (φ : Proposition Atom)
    (h : IValid.{_, 0} φ) : intuitionisticTableau φ = .closed
-- Tableau/Intuitionistic/Completeness.lean:178

theorem minimalTableau_complete (φ : Proposition Atom)
    (h : MValid.{_, 0} φ) : minimalTableau φ = .closed
-- Tableau/Minimal/Completeness.lean:170
```

These say exactly what completeness should say. The extra premise is discharged at each call
site, and it is not an artificial device: `MValid` (`Semantics/Kripke.lean:153-160`) *already*
requires `bot_forces` to be upward-closed as part of its definition of a minimal Kripke model, so
the added conjunct mirrors a condition the semantics imposes anyway. At the intuitionistic call
site `bot_forces = fun _ => False`, which is trivially upward-closed, so the premise costs
nothing there.

An independent adversarial pass reached the same verdict by a different route, and added the
decisive point: the conjunct is an **obligation the countermodel owes**, not a hypothesis
smuggled into the conclusion — it made the theorem *harder* to prove, not weaker. Omitting it
would make the theorem false, and the repository machine-checks exactly that:
`CslibTests/MvalidBotShapeRefutation.lean` exhibits `φ = ⊥ → ((⊥ → ⊥) → ⊥)`, which is `MValid`
while the old conjunct-free `hvalid` body is false.

**Verdict: confirmed clean, not weakened.** This was the most likely place for the recent work to
have quietly broken something, and it did not.

## Critical Issues

### C1. Instance-resolution regression: the tableau `Tautology` decider is inert under `decide` and shadows the working one

**File**: `Cslib/Logics/Propositional/Tableau/Classical/DecisionProcedure.lean:81`

**Description**: Two instances target `Decidable (Tautology φ)`:

- `instDecidableTautology` (`Semantics/Bool.lean:185`) — Boolean enumeration, requires
  `[Fintype Atom]`, **reduces in the kernel**.
- `instDecidableTautologyTableau` (`Tableau/Classical/DecisionProcedure.lean:81`) — tableau,
  needs no `Fintype`, and **does not reduce in the kernel**: it stalls on `WellFounded.fix`.

Both have default priority, so the tableau instance — declared later — wins resolution wherever
both are in scope. `Cslib.lean` imports both (`:597` and `:627`), so **any consumer of the
barrel gets the inert one**.

**Reproduced directly in this review.** A probe importing both files:

```
#synth Decidable (Tautology (Atom := Bool) (.imp (.atom false) (.atom false)))
-- ⇒ instDecidableTautologyTableau

example : decide (Tautology ... ) = true := by decide
-- error: Tactic `decide` failed ... After unfolding the instances `instDecidableEqBool`,
-- `Bool.decEq`, and `instDecidableTautologyTableau`, reduction got stuck
```

**Impact**: `CslibTests/Propositional.lean:64-90` contains 7 `by decide` tautology tests that
pass **only because that file does not transitively import the tableau module**. They are one
import away from breaking, and the breakage is invisible until someone adds it. More seriously,
downstream users importing `Cslib` cannot use `decide` on `Tautology` at all — the library
silently hands them a decider that cannot run in the kernel.

This is the one finding in this review that is a **defect in the code**, not in the prose.

**Fix, verified in this review**: one line —

```lean
attribute [instance 100] instDecidableTautologyTableau
```

With it, `#synth` resolves back to `instDecidableTautology` and all the `decide` examples
compile clean. The tableau instance remains available for the `Fintype`-free case where it is
the only option.

**Related**: the underlying `#eval`/`decide` split is not itself a bug and is documented at
`CslibTests/TableauConformance.lean:30` ("`decide`, `native_decide`, and `rfl` stall on
`WellFounded.fix`"). The algorithms genuinely compute under `#eval` — verified: 20 `#guard_msgs`
conformance rows green, and spot checks give correct verdicts (`minimalTableau (⊥ → p)` → open,
correctly rejecting ex falso). See M4.

### H3. The three logics are proved *ordered* but never proved *distinct* — and one docstring overclaims it

**File**: `Cslib/Logics/Propositional/Semantics/Algebra/ConservativeChain.lean:140`

**Description**: The docstring asserts the five Hilbert systems are **"strictly ordered"** by
derivability. What `derivability_subsumption_chain` actually proves is one-way subsumption over
three displayed nodes. **Strictness is never proved.** An exhaustive search of the tree found
**no properness or separation result anywhere** — nothing establishes that MPL ⊊ IPL ⊊ CPL.

**Impact**: The library proves the three logics are ordered; it does not prove they are
different. Concretely, nothing rules out a (false, but unrefuted in-tree) reading in which the
inclusions collapse. This matters for any claim of the form "three distinct propositional logics
formalized" — the separations are exactly the results that would justify it, and they are absent.

There is a wrinkle worth recording: the natural route to a separation is exhibiting a formula
(e.g. `p ∨ ¬p`, or Peirce's law) that one system decides and another does not — which would
naturally be discharged by `decide` on the tableau. Per **C1**, that is precisely what does not
reduce. The two findings interact.

**Recommended fix**: Two separable pieces. (a) Correct the docstring to say "ordered" rather
than "strictly ordered" — immediate, and the honest statement of what is proved. (b) Decide
whether the separation theorems are in scope; if yes they are real new mathematics, not a
cleanup. Do not silently leave (a) unfixed on the expectation that (b) will happen.

### M5. `ctxToImp`'s noncomputability is a real design choice, not a trivial oversight

**File**: `SequentCalculus/LJ/Decidability.lean:82`

**Description**: This refines M2. The root cause is that `Multiset.toList` is itself
`noncomputable` in Mathlib (`Multiset/Basic.lean:33`, "Produces a list of the elements in the
multiset using choice"). Picking a list order for a `Finset` is a genuine choice: distinct
orders give distinct — though interderivable — formulas. `Finset.fold` does not apply, since
`imp` is neither commutative nor associative, and `Hashable` supplies no total order.

So there are two honest routes, and they differ in cost:
1. Add `[LinearOrder Atom]` and use `Finset.sort` — computable, but a **new hypothesis on the
   public instances**.
2. Restate over `List` contexts — `listToImp` (`:72`) and the list-level lemmas
   `ljListDeductionFwd:91` / `Bwd:130` (LK's `:65`/`:110`) are **already plain computable defs**;
   only the `ctxToImp`-wrapped `:112`/`:170` and the four instances inherit the taint. Cheapest
   real fix.

**Separately verified as harmless**: the FMP-based deciders
(`IntDecidability.lean:489`, `MinDecidability.lean:445`) are noncomputable for a *deeper* reason
(`Fintype.ofInjective` inverts an injection via choice) — but they are deliberately plain `def`s,
**not registered instances**, with the computable tableau instance canonical. So every
*registered* `Decidable` instance in the subsystem is computable except the four LK/LJ
context-based ones. That is exactly the set M2 identified, and the only set worth acting on.
