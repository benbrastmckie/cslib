**The recognizer-reduction roots (275 negPos, orPos/impPos cascades, 624 negNeg) are NOT
mechanical drift — they are a genuine reduction-order / proof-structure problem.** Authoritative
analysis (from reading Defs.lean recognizers + PropositionalRules.lean applyPropRule/tryAllPropRules):

- `tryAllPropRules` order = `[andPos, andNeg, orPos, orNeg, impPos, impNeg, negPos, negNeg]`,
  selected by `results.find? (·.isApplicable) |>.getD .notApplicable`.
- In the `| imp a c => cases c with | bot =>` arm, `formula = a → ⊥ = .imp a .bot` with `a` ABSTRACT.
- `modalNegOf? (.imp a .bot) = some a` (has @[simp] `modalNegOf?_neg`, reduces). negPos WOULD fire.
- BUT `modalAndOf? (.imp a .bot)` (pattern `.imp (.imp _ (.imp _ .bot)) .bot`) and
  `modalOrOf? (.imp a .bot)` (pattern `.imp (.imp _ .bot) b`) are STUCK for abstract `a`
  (no @[simp] lemma covers `.imp a .bot`; the match can't decide whether `a` is itself `.imp _ .bot`).
  Because andPos/orPos appear BEFORE negPos in the rule list, `find? (·.isApplicable)` is stuck on
  these undecided earlier results and never reaches negPos. => `hsf` (the ~400-line
  `match …tryAllPropRules… = some (newBs,newExps,newAcc)`) never collapses => the `obtain`'s
  dependent elimination fails (errors at 275/624) and the downstream `subst hnewBs`/refs become
  `Unknown identifier hnewBs` (the ~46-error cascade).
- SEMANTIC SUBTLETY: this is not only a reduction failure. If `a = x → ⊥`, then
  `a → ⊥ = (x→⊥)→⊥ = x ∨ ⊥`, so `orOf?` genuinely fires and the applicable rule is orPos
  (branching), NOT negPos. The current arm handles `a → ⊥` UNIFORMLY as negPos
  (`refine ⟨[⟨.neg, a, lbl⟩] ++ b, …⟩`), which is only valid when `a` is not a negation/conjunction.
